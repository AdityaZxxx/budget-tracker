## Issues resolved (this effort)

The 2026-11-10 verification run found two product gaps, fixed in [#15](https://github.com/AdityaZxxx/sora/pull/15):

1. Choosing a category in the create-transaction dialog threw `Maximum update depth exceeded` and killed the page. `CategoryPicker` called its parent from an effect whose dependency was a new function each render. The effect now only reports a value change.
2. Signing in against the production bundle left a blank page. The auth pages linked the dashboard, the prefetch cached the sign-in redirect, and the router reused it after a successful sign-in. The auth pages no longer link the dashboard.

The hardening series, 2026-11-13 to 2026-11-14 ([#49](https://github.com/AdityaZxxx/sora/pull/49) to [#67](https://github.com/AdityaZxxx/sora/pull/67)), fixed what the harness surfaced at each seam instead of at one transport:

- **System-category integrity.** The `Settlement` anchor row could be deleted through `delete_category`, corrupting the balance math. The guard now sits in one helper both verbs call ([#54](https://github.com/AdityaZxxx/sora/pull/54)).
- **Errors.** The seam throws typed `DomainError`s; every transport surfaces the server's own sentence; unexpected errors get a generic message instead of internals ([#51](https://github.com/AdityaZxxx/sora/pull/51), [#62](https://github.com/AdityaZxxx/sora/pull/62), [#63](https://github.com/AdityaZxxx/sora/pull/63), [#64](https://github.com/AdityaZxxx/sora/pull/64), [#65](https://github.com/AdityaZxxx/sora/pull/65)). This resolves a production-only symptom noted earlier: minified React error 441 wherever a client toasted `error.message` from a server action. `CreateTransactionDialog`, `UpcomingBills`, and `RecurringItemDialog` now render the action's `message`; the identical journey shows the real sentence (`Hard budget exceeded for Utilities: ...`), verified in this pass.
- **Input rules.** Field rules are written once and reused ([#50](https://github.com/AdityaZxxx/sora/pull/50), [#52](https://github.com/AdityaZxxx/sora/pull/52), [#56](https://github.com/AdityaZxxx/sora/pull/56)); the CLI validates like the server before it calls ([#58](https://github.com/AdityaZxxx/sora/pull/58)); form controls validate, not just submit ([#59](https://github.com/AdityaZxxx/sora/pull/59)); `createHousehold` validates the name ([#57](https://github.com/AdityaZxxx/sora/pull/57)); the recurring seam parses its own input ([#53](https://github.com/AdityaZxxx/sora/pull/53)); every exported `lib/` writer must parse its own schema, enforced by a vendored lint rule ([#67](https://github.com/AdityaZxxx/sora/pull/67)).
- **Contracts.** Money rules tightened across web and MCP ([#60](https://github.com/AdityaZxxx/sora/pull/60)); delete contracts standardised ([#61](https://github.com/AdityaZxxx/sora/pull/61)); the role seam enforces the role itself, closing two surfaces that had no role check at all ([#55](https://github.com/AdityaZxxx/sora/pull/55)); settlement counterparties tracked by member id with a migrating resolver and trigger ([#66](https://github.com/AdityaZxxx/sora/pull/66)); the dashboard card baseline in shared primitives ([#49](https://github.com/AdityaZxxx/sora/pull/49)).

This final pass found and fixes one more issue:

3. Unauthenticated requests to the session-guarded API routes were answered with a redirect to the HTML sign-in page (`307`, then `200 text/html` when followed) at two layers: `proxy.ts` redirected `/api/*` without a session cookie, and each of the twelve route handlers redirected when `requireHousehold()` returned null, which also covered a present-but-invalid session (for example, after expiry). Client fetchers call `response.json()` on that HTML and throw `SyntaxError`, observed in the app's console as `Error fetching stats: Unexpected token '<'`. API routes now answer `401 {"message":"Unauthorized"}` in the same `{ message }` shape the routes use for rejections; page routes still redirect to `/sign-in` as browsers expect. `/api/auth/*`, `/api/cron/*`, and `/api/mcp*` are unchanged. The seven client fetchers that never checked `response.ok` were given the same guard (they would otherwise have started resolving with a junk-shaped object and crashing at render, e.g. `Insights` on `months.some`), so a dead session lands react-query in its error state exactly as before.

   Re-verified as run `20261114T165908Z-30107` on this branch: `doctor` is clean; all twelve session-guarded routes answer `401 {"message":"Unauthorized"}` (and with a present-but-invalid session cookie, same); page routes still `307` to `/sign-in`; `/api/cron/digest` and `/api/mcp` unchanged; a fresh sign-in renders the dashboard; and under a dead session the page's polls land as 401s and the app's own action-redirect machinery ends the tab on `/sign-in`, with no `SyntaxError` in the console.

## Remaining concerns

- **No test suite, by decision.** CI, the lint plugin, and the verification harness carry the weight. If the product grows past friends and family, the seam is where to add tests first.
- **Google sign-in is not verified end to end.** The button renders always; without `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` the flow cannot complete. Consider hiding the button when the credentials are absent, or document that it is unconfigured until the keys land.
- **Email verification, password reset, and the daily digest are unverified.** They need Resend credentials. The digest cron answers 401 without its secret; that is all that could be proved here.
- **The native date input in the create-token dialog cannot be driven by browser automation** (`input[type=date]` lives in the browser's UI, not the page), so the expiry path was verified by setting the value through the DOM. A human click on the calendar works; knowing this avoids false bug reports from the harness.
- **`control-sora reset` under a signed-in tab** leaves the page polling with a dead session; before the 401 fix it logged `SyntaxError`, after it, the fetchers land in react-query's error state. Reset goes last in future runs.
- **Console noise on the dashboard:** none observed after the 401 fix beyond the expected poll retries on a dead session.
